# 버전 운영 지침

2026-11-06부터 적용합니다. 현재 앱을 새 **1.0.0** 기준판으로 정리한 이후의 제품 변경에 사용합니다. 현재 숫자는 `local_app/config.py`의 `VERSION`이 기준이며 아래 파일은 그 값을 맞춰 적는 배포 메타데이터입니다.

[SemVer 2.0.0](https://semver.org/lang/ko/)의 `MAJOR.MINOR.PATCH`를 따릅니다. 이 앱에서 호환성의 대상은 공개 Python 라이브러리만이 아니라 저장된 재고·회차·설정·백업, 사용자에게 제공한 API/입출력과 기존 기능을 정상 사용·업그레이드하는 계약입니다.

## 무엇을 올리는가

| 종류 | 판단 | 예시 | 1.0.0에서 다음 번호 |
|---|---|---|---|
| PATCH | 기능·데이터 계약을 유지하는 오류 수정, 소규모 UI·성능·자원 관리 개선 | 버튼 이동·스타일, 누락 이미지 복구, 중복 차감 방어, 같은 방식의 검증 표본 확장 | 1.0.1 |
| MINOR | 기존 기능과 저장 데이터를 보존하면서 새 기능·사용 흐름 추가 | 새 사용자 설정, 새 캡처 입력 경로, 새 작업실·제작 기능 | 1.1.0 |
| MAJOR | 이전 저장·백업·입출력·연동이나 정상 사용 계약을 깨는 변경 | 기존 백업을 더 이상 읽지 못함, 호환되지 않는 API 제거·형식 변경 | 2.0.0 |
| 번호 유지 | 실행 제품이 변하지 않는 설명·기록·테스트·제품 외 검증 도구만의 변경 | README 오탈자, 이력 근거 보충, 동작 변화 없는 테스트 추가 | 1.0.0 |

자동 마이그레이션으로 기존 데이터를 계속 사용할 수 있는 스키마 추가만으로 MAJOR라고 정하지 않습니다. 내부 파일 분리만으로 MAJOR가 되지도 않습니다. 스케줄 선택 정책·인식 확정 기준을 바꾸는 작업은 변경 줄 수로 PATCH라고 단정하지 말고 해당 작업 지침에서 사용자 영향과 계약을 확인합니다.

작은 제품 수정도 완료해 새 판을 제공한다면 PATCH를 올립니다. 기능 추가와 버그 수정을 한 작업에 묶으면 가장 큰 변경 등급 하나로 정하며, MINOR/MAJOR 상승 시 하위 숫자는 0으로 초기화합니다.

## 번호를 올리는 단위

- **독립적으로 완료·인계하는 제품 변경 묶음당 한 번** 올립니다. 커밋 수·파일 수·대화 메시지 수만큼 올리지 않습니다.
- 같은 작업의 구현·검사·실패 수정·재검사는 하나의 묶음입니다. 이어서 작업하라는 지시만으로 이미 올린 버전을 다시 올리지 않습니다.
- 이미 완료·설치한 판에 다음 수정이 생기면 새 번호를 씁니다. 이전 버전의 변경 이력에 새 제품 변경을 조용히 덧붙이지 않습니다.
- 사용자가 버전 기록을 따로 말하지 않아도 제품 작업의 마무리에 포함합니다. 단, 실험·검토만 했거나 변경을 반영하지 않았다면 현재 제품 버전을 올리지 않습니다.
- 문서·테스트·제품 외 검증 도구만 수정했다면 번호 유지 사유를 완료 보고에 적습니다. 제품 변경을 단순 문서 수정이라고 분류해 생략하지 않습니다.
- 현재 자동 확인 명령은 정식 숫자 `X.Y.Z`를 사용합니다. 개발 후보는 Git SHA/산출물 해시와 후보 상태로 구분하며, 필요 없이 `v21`·날짜 문자열·새로운 버전 파일을 추가하지 않습니다.

## 작업 시작

1. 루트 `AGENTS.md`, 이 지침, `CHANGELOG.md`의 최신 항목과 `Unreleased`를 읽습니다.
2. `python -B tools/check_version.py`로 현재 번호를 확인합니다. 불일치가 있으면 기존 작업의 완료 여부와 실제 기준을 조사하고, 더 큰 숫자로 무조건 덮어쓰지 않습니다.
3. `git diff`와 현재 앱·패키지 상태를 필요한 범위에서 확인합니다. 다른 작업의 미커밋 변경을 이번 작업이나 릴리스로 임의 편입하지 않습니다.
4. 변경 등급과 현재 작업 묶음을 판단합니다. 이미 같은 작업에서 예약한 버전이면 그대로 마무리합니다.

## 제품 변경을 마무리할 때

1. 관련 검사에서 통과한 구현을 확정합니다. `Unreleased`의 해당 변경을 새 `## [X.Y.Z] - YYYY-MM-DD` 항목으로 옮깁니다. 날짜는 한국 시간 기준입니다.
2. `local_app/config.py`의 `VERSION`을 새 숫자로 갱신합니다.
3. 아래 메타데이터와 README를 **같은 작업에서** 맞춥니다.
4. 새 변경 이력에는 사용자 관점의 변경·수정, 실제 검사와 미검증 범위, 앱 반영 여부를 적습니다. 계획이나 실패한 실험을 완료 기능으로 넣지 않습니다.
5. `python -B tools/check_version.py`, `git diff --check`를 실행합니다. 버전 정리만으로 전체 회귀를 반복하지 않습니다.
6. 새 버전 번호, 변경 등급·이유, 검사 결과, 설치/커밋/푸시 여부를 간결하게 보고합니다.

### 함께 갱신하는 위치

| 파일 | 필드 |
|---|---|
| `local_app/config.py` | `VERSION` — 단일 기준. `/suite-health` 응답에서 사용 |
| `pyproject.toml` | `[project].version` |
| `package.json` | 최상위 `version` |
| `package-lock.json` | 최상위 `version`, `packages[""].version`만. 의존성 버전은 변경하지 않음 |
| `local_app/packaging/version-info.txt` | 문자열 `FileVersion`/`ProductVersion`, 숫자 `filevers`/`prodvers` |
| `README.md` | `현재 버전: **X.Y.Z**` |
| `CHANGELOG.md` | `Unreleased` 다음의 최신 확정 항목 |

Windows 숫자 버전은 `(MAJOR, MINOR, PATCH, 0)`, 문자열 버전은 `MAJOR.MINOR.PATCH`입니다. 확인 명령이 위 위치의 불일치를 검출합니다. 버전 변경을 위해 `npm install`이나 의존성 업데이트를 실행할 필요가 없습니다.

## 소스·설치·Git 공개는 구분한다

- 버전 파일과 변경 이력을 갱신했다고 실제 설치 앱이 바뀌지는 않습니다. 소스 버전·패키지/설치 상태·Git 태그/Release 유무를 구분해 보고합니다.
- 사용자가 앱 반영을 요청했을 때만 기존 정상 종료·DB/ROI/설치 백업·검사한 패키지 교체·재시작·해시/상태 보존 확인을 수행합니다. 실행 중 DB를 문서 검사에 사용하지 않습니다.
- 실제 `/suite-health`의 숫자뿐 아니라 설치 자산 해시도 확인해야 같은 버전의 다른 소스/정적 파일을 잘못 적용한 일을 구분할 수 있습니다.
- **이 지침은 commit/push/merge/tag/GitHub Release 생성 권한을 부여하지 않습니다.** 사용자가 요청한 Git 작업만 수행합니다. 공식 태그를 만들도록 요청받으면 확인된 릴리스 커밋에 `vX.Y.Z`를 붙입니다.
- 번호를 올린 뒤 커밋되지 않은 상태도 사실대로 보고합니다. 커밋을 하지 않았다는 이유로 새로 완료·설치한 제품 판의 버전 기록을 생략하지 않습니다.

## 역사·자료 버전의 경계

[프로젝트 역사](../PROJECT-HISTORY.md)의 `0.x`는 2026-11-06에 재구성한 회고용 구분이며 실제 과거 태그·출시를 뜻하지 않습니다. `1.0.0` 이후 일반 패치는 `CHANGELOG.md`에 이어 적고, 역사 문서는 큰 전환이 있을 때 보충합니다.

과거 `VERSION`, `v14`, `v21`, SPEC 번호나 날짜가 붙은 카탈로그·정답 사전·숫자 프로필 버전은 앱 버전과 다른 식별자입니다. 사전 내용·스키마·동결 fixture·원본 해시를 이 지침의 숫자로 일괄 치환하지 않습니다. 앱 버전 상승만으로 정답 사전을 다시 만들지 않습니다.
